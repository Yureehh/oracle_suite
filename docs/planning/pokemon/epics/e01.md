- Domain: project workflow / quality.
- Status / priority / size / dependencies: [PKA-067 board entry](../kanban.md); this recurring audit story has no prerequisite.
- Proposed approach: run a repository Ponytail audit after an epic milestone or roughly three to five completed behavioral stories, whichever comes first. Audit before the first substantial training run or public release, and after major simulator, observation, action or persistence changes. Use focused change reviews between milestones; do not audit the whole repository after every commit.
- Likely components: the affected code, workload tests, docs/audits/ and relevant planning cards. No scheduled automation or new tooling dependency.
- Acceptance criteria: a dated report identifies the inspected commit, scope, exercised workload, ranked findings, reproductions and remaining limits. Link each actionable finding to an existing story or append a small repair card; distinguish observed defects from hypothetical concerns. Update the next audit trigger. Owner acceptance and publication remain separate decisions.
- Validation/testing: reproduce suspected bugs before changing code; run focused regressions and required repository checks for approved repairs. Simplify only where behavior remains verified and the affected scope warrants it.
- Learning focus: whole-repository audits versus focused reviews; evidence before refactoring.
- Decisions/risks: prioritize simulator fidelity, information leakage, paired-action legality, concurrency, durability and measured training bottlenecks. Avoid speculative abstractions and cleanup based solely on line count.
